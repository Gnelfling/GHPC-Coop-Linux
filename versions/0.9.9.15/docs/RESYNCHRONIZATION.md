# Vehicle resynchronization

This document describes the local PvE hardening candidate (wire protocol 26).
It is not the behavior of the published 0.9.9.14 DLL. Both test clients must use
this candidate; protocol 25 peers are intentionally incompatible.

## What triggers recovery

- Every initial vehicle claim completes a baseline handshake before input is accepted.
- The host notices additions/removals in the active vehicle roster.
- A guest rejects a normal snapshot because identities or component counts differ.
- Vehicle snapshots stop for three seconds while the connection remains alive and
  the host is neither paused nor in AAR.
- A successful vehicle switch establishes a new baseline for the new reservation.

Ordinary snapshots remain complete state updates at the existing send cadence.
Recovery is not a second damage simulation and does not predict hits.

## Handshake

1. The host clears the affected peer's held throttle, steering, trigger and reload.
   The existing reservation and manual crew control remain in place; AI does not
   take over the vehicle. Other peers continue normally.
2. The host sends `ResyncBaseline` with a unique host sequence, roster revision,
   assigned unit, technical layout signatures, vehicle poses, damage, ammunition,
   detached parts, equipment, fire, objectives, support and weather.
3. The guest validates the entire roster before applying state. A matching native
   vehicle that has not spawned yet is retried every 250 ms, within a 15-second
   recovery deadline. No vehicle is guessed by position or display name.
4. On success, the guest discards old interpolation history and applies the baseline.
   Vehicles absent from the host roster are deactivated locally, with cleanup
   restoration recorded. Cumulative shot/smoke/explosion counters seed history;
   old events must not fire again. The guest then sends `ResyncAck`.
5. The host accepts only the current sequence, revision and owned unit, then sends
   `ResyncReady`. The guest resumes input after that exact confirmation.

Inputs include both the roster revision and accepted baseline sequence. An input
from before recovery is rejected even if the roster revision did not change.
A late acknowledgment cannot unlock a newer recovery. Reliable transport preserves
baseline/confirmation ordering; snapshot coalescing cannot cross those messages.
Heartbeats continue during recovery. A timeout closes only the affected host peer.

## Identity and native lifetime

`Game/Replication/GameBridge.Roster.cs` retains existing native vehicle records.
It never calls the destructive initial `Capture()` to repair a running session.
Authored dynamic spawn points are cached at mission capture. Their fixed hierarchy
and anchor keys are cached too, so later sibling removal cannot change those keys.
Membership is inspected every two seconds without a whole-scene object search.
New authored vehicles receive the same spawn-slot IDs on both machines, cached
component layouts, and guest AI/physics suppression.

New eligible friendly vehicles are added to selection choices without replacing
occupied seats or increasing the room's established player capacity. Destroyed or
inactive units are still unavailable for takeover.

## Deliberate failure boundaries

- Recovery matches native objects generated by the same mission. It does not
  instantiate arbitrary network-supplied prefabs or invent a missing vehicle.
- A vehicle that never exists on the guest, a reused spawn-slot identity, a changed
  technical layout, or removal of the currently owned native object cannot be
  safely repaired by rebinding to another tank. These fail with a diagnostic.
- Runtime-created spawn points outside the authored point set are not discovered.
- Native damage callbacks are not reversible transactions. If one throws during
  application, the guest does not acknowledge partial success; normal error
  handling tears down that session.
- AAR shot history/independent shot selection and infantry/aircraft replication
  retain their existing implementations. This handshake repairs ground vehicles.

## Code map and tests

- `Networking/Resync/ResyncGate.cs`: host transaction/ownership gate.
- `Networking/Resync/RosterBaselinePlan.cs`: pure baseline preflight.
- `Networking/Resync/SnapshotValidation.cs`: ordinary snapshot preflight.
- `Networking/Resync/CoopLabMod.Resync.cs`: orchestration, deadlines and diagnostics.
- `Game/Replication/GameBridge.Roster.cs`: native discovery and baseline application.
- `ResyncTests.cs`: wire state preservation, stale acknowledgments/inputs, ownership,
  delayed spawns, roster changes and peer isolation.
- `SteamAdapterTests.cs`: actual Steam adapter queue with a fake transport; baseline
  and confirmation remain ordering barriers under backpressure.

The pinned build and fixtures do not replace a two-PC Unity playtest. Before release,
verify reinforcement appearance, wreck removal, vehicle switching, held-fire recovery,
mission exit/rejoin, and a slow guest while another guest continues moving. Look for
`RESYNC begin`, `RESYNC acknowledged`, and `RESYNC complete` with matching sequences.
No game is launched or public release updated by this local change.
